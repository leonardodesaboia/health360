# physician-reader Specification

## Purpose

Provide a dataset-scoped physician queue and read-only workspace for exact analysis, profile and evidence versions, preserving unknown data and explicit demonstrative boundaries.

## Requirements

### Requirement: Dataset-scoped physician queue

The server SHALL list only the current demo dataset's patient analyses with actual analysis timestamps and versioned workspace links.

#### Scenario: No demo session

- **WHEN** the physician opens the queue without a demo session
- **THEN** no patient records are disclosed and a selection prompt is shown

#### Scenario: Current analysis

- **WHEN** the dataset contains multiple analysis versions
- **THEN** the queue displays the newest analysis for the session patient with its stored creation time

### Requirement: Versioned preliminary reader

The workspace SHALL expose the referenced profile, examinations, proposal category, rationale, criteria, versioned evidence, unknown data and uncertainty with demonstrative and preliminary labels.

#### Scenario: Foreign or invalid identifier

- **WHEN** an identifier is absent from the scoped dataset or belongs to another patient
- **THEN** the workspace returns no patient information

#### Scenario: Stale analysis

- **WHEN** a newer profile, context or analysis exists
- **THEN** the reader warns that the analysis is stale

#### Scenario: Unknown data and evidence

- **WHEN** a profile fact or evidence reference is unavailable
- **THEN** it remains explicitly unknown or placeholder and is never presented as confirmed

#### Scenario: Responsive keyboard reader

- **WHEN** the workspace is read on mobile or desktop with a keyboard
- **THEN** context and proposal disclosures remain accessible without horizontal page overflow

### Requirement: Explicit analysis-output provenance

The physician reader SHALL distinguish usable AI explanations from blocked system-generated status and rule-generated context. Stored provider configuration SHALL NOT imply that a blocked summary was generated by a model.

#### Scenario: Rule-blocked analysis without a model call

- **WHEN** the real analysis producer blocks on missing information before invoking the model
- **THEN** the reader labels the summary as blocked system/rule output, preserves its version metadata and omits provider/model attribution

#### Scenario: Preliminary model explanation

- **WHEN** a validated preliminary analysis is available
- **THEN** the reader identifies its explanation as AI-generated and displays its actual provider/model audit metadata

### Requirement: Populated reader accessibility

The populated physician queue and workspace SHALL support accessible reading on desktop and mobile, including the table/list, disclosures and source links.

#### Scenario: Populated accessibility scan

- **WHEN** a seeded analysis is read through the queue and workspace on desktop or mobile
- **THEN** serious and critical axe checks pass for both populated screens and keyboard evidence disclosures remain usable

### Requirement: Explanatory read-only blocked workspace

The reader SHALL show a provenance-labeled plain-language outcome reason for blocked analyses, without decision controls, generic review tasks or proposal decision counts. It SHALL retain the patient-status link and demonstrative labels.

#### Scenario: Symptoms exclude the screening demonstration

- **WHEN** Daniel's analyzed profile reports rectal bleeding and the evaluator returns OUT_OF_SCOPE
- **THEN** the physician sees that symptoms were reported, this screening demonstration does not apply, and symptoms need assessment by a clinician; no save or finalize controls appear

#### Scenario: Failure provenance

- **WHEN** a blocked analysis represents provider failure or missing information
- **THEN** the read-only explanation distinguishes retryable system failure from clarification without implying that a model generated a deterministic exclusion
